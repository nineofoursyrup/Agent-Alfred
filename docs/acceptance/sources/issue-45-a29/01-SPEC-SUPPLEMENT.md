## 1. 本次已批准的产品裁决

### 1.1 范围与完成条件

Session/批次选择绑定可展示的固定历史范围，确认时冻结成员。不自动涵盖以后所有新 Run，但沿实际读取关系产生的后继仍隔离。部分确认后，只要还有未解决范围就保持 needs_scope。范围全部确认且受管清理成功，才可进入 complete；不得通过一次确认推断全局来源完整。

### 1.2 等待确认期间的读取

已知闭包立即隔离。无法证明安全、仍待确认的历史组，暂停进入工作窗口、gate、工具账摘要及提炼；可证明无关的组继续使用。证据不足以缩小未知范围时，应明确展示较大的暂停范围，不得擅自限定为当前 Session。历史仍可人工查看，允许用当前新输入继续聊天。

## 2. 范围身份、展示和确认

### 2.1 身份与证据

遗忘由原 delete 的稳定 `operation_id` 标识。范围属于该遗忘操作，不能拿别的操作或别的记录的范围来确认。记忆身份为 `(kind, memory_id)`，内容版本独立；已知来源/使用链应覆盖该 ID 的相关历史版本，不能只查删除前最新版本。

来源组身份区分 Run 与提炼 batch，均为不透明 ID。Session 是选取历史范围的容器，不等于一个 Run，也不等于自动永久禁用该 Session。批次来源可能跨 Session，不能由当前页面 Session 替代。

每个供确认的范围具有服务器签发的稳定 `scope_id`、`scope_revision`、范围类型、所属容器 ID、可展示的边界和成员集合。成员按完整组处理；不做句子级语义猜测。集合过大可以有一致快照分页；首屏、计数与后续页必须属于同一版本。

范围展示仅需安全元数据：身份、时间边界、组数、Session/批次 ID、缺证原因及暂停范围。原始聊天可从独立人工历史入口打开；正文、subject、会话标题中的原话、查询、异常散文不得复制进确认回执、关联表或清理任务。

无法还原完整 Run/批次关联的旧历史必须保留“无法归组/无法证明关联”的缺口。范围可用服务器持久化的旧历史成员映射覆盖这些内容，但不得伪造 Run、把缺失 ID 丢掉，或迁移成 known_none。只有真实的明确手动无历史来源可使用 known_none。

### 2.2 展示、确认和冻结的线性化点

1. 展示生成可重读的范围版本，包含确切成员及其证据边界；显示的是本次历史快照，不是动态 Session 查询。
2. 确认提交该版本的范围身份。在共享 MutationGate 的有效权限内，由同一 SQLite 事务核对范围身份、版本、操作归属及当前待确认义务。
3. 确认事务提交是成员冻结的权威时点。冻结的是用户已看到并确认的确切集合，不能在事务内重新查询“Session 全部历史”后静默添加成员。
4. 展示后新生且可证明无关的 Run 不改变已展示成员，也不被 Session 身份自动隔离。若新的证据改变原范围的成员或待确认义务，旧确认必须拒绝为陈旧范围，重新展示；不能替用户扩选。
5. 同事务写入冻结成员、确认回执、隔离闭包及 SQLite 内的投影/候选失效，更新相应读侧版本。提交前没有成功确认；回滚时共同不成立。

已隔离组后来发现或产生的实际读取后继，属于已批准的传播规则：传播隔离，保留其因果边，不修改当时冻结成员，不要求用户再次确认同一传播含义。仅仅与冻结成员同属 Session、内容相似或时间更晚，不构成后继关系。

### 2.3 迟到确认与幂等

确认动作建议另有稳定 `action_id`，区别于原删除 `operation_id`。相同 action_id、相同参数先回读原确认事实；当前遗忘进度另读，不能把旧进度当当前状态。响应丢失、重启及重复点击均不重复扩大隔离。

同 action_id 不同参数拒绝；旧审计 key 无法比较时拒绝重做，安全历史回执仍可查询，沿用 operation_mismatch / operation_unverifiable 语义。请求没有有效成功回执才进行 expected scope revision 核验。已经成功但响应迟到的重送不能因后续 revision 变化而被误判“从未确认”。

无成功回执的旧版本、属于其它遗忘操作的 scope、用户伪造的成员列表均不得执行。建议安全码分别为 scope_stale / invalid_input；具体传输映射见接口准备文档。两标签并发确认由同一准入与事务排序；busy 不排队，陈旧请求不能覆盖已经确认的事实。

### 2.4 重启

持久保存遗忘操作、范围版本、已展示快照、冻结成员、确认动作身份、来源完整性、关联、隔离/暂停事实和清理进度。恢复完成且读闸可判定前，不开放自动历史读取。

重启不把未知范围变安全、不清空暂停、不重新解释 Session 为当前全部成员。仅进程内通知身份重置；范围与操作身份保持有效。不能单靠内存、SSE、trace 回放或某次 Run 的成功终态恢复这些事实。

## 3. 自动读取与传播

### 3.1 三类事实分开

- 已隔离：已知受影响来源、用户确认冻结的成员、直接使用者及沿实际读取链传播的后继。自动读取拒绝，人工历史仍可查看。
- 待确认而暂停：无法证明安全的历史范围。自动读取拒绝，但不声称已确认污染或已完成永久范围选择。
- 可证明无关：在本次证据覆盖下有可验证的不相关依据，且不在任何遗忘操作的隔离或暂停集合中，允许自动使用。

允许自动使用的判据是有安全依据且不受任何操作限制；“没有查到关联边”或“不是当前 Session”都不是安全依据。一个组被多个遗忘操作限制时，处理其中一个操作不能解除另一个操作的限制。

### 3.2 未知范围扩展与收敛

证据能界定在某个历史容器内时，展示该容器的确切暂停成员及理由；不能界定时，暂停并展示更大集合，必要时覆盖所有无法证明安全的既存历史，跨 Session/批次也相同。不能以当前 Session、当前窗口 N 轮或页面筛选作为隐含上界。

无法枚举或读取证据本身失败时，返回安全故障及无法确认的范围状态，不以空集合提供“全部安全”的结论。允许当前新输入继续聊天，不依赖失败的历史读取；门与回答都使用同一批经过过滤的工作窗口。当前新输入并非旧历史副本，仍按正常聊天预算和其他已有失败规则处理。

部分确认只解决选定的待确认义务；其它未知组继续暂停。一个组的暂停只能在该组已被明确确认纳入隔离，或取得可核验的无关证据后解除；前者仍处于隔离，不能因此被放行。证据缩小必须有完整性依据、持久记录与可展示原因，不得用一次确认把未选范围批量标成无关。

该规则约束工作窗口、gate 历史输入、工具账自动摘要和提炼来源。原始会话/既有 trace 的人工查看、独立同义 Memory 记录保留，以及新的明确保存权利仍按 R09；不新增文本或 HMAC 内容黑名单。

### 3.3 在途和晚到关联

读取准入必须检查当前隔离/暂停版本；已经取得的正文快照在真正自动使用前也要遵守有效性检查，失效时丢弃或重新获取安全投影。由 #16/#19/#18 实际消费者接入，不能只有页面过滤。

持久关联区分 Memory→来源组、Run/Attempt→实际 Memory 版本、Run/Attempt→实际历史组；gate 和 answer 均记录实际使用，不从 selected 推断已发送。完整性未知的历史不能因没有落定 telemetry 而被判为无使用。

晚到关联的登记和由此产生的隔离/暂停传播、SQLite 投影失效必须原子生效，不能先发布“可安全读取”再异步补隔离。已隔离后继继续传播隔离；暂停来源的已知读取后继至少保持暂停，源范围确认为隔离后继续传播。新 Run 若未读取受限历史且有证据证明无关，不因所属 Session 被一并隔离。

## 4. 遗忘状态

删除的不可变提交回执与可变遗忘进度分开。以下状态只在数据库删除已确认提交后存在；A54 屏障失败或删除事务回滚时，只返回安全未执行/失败信息，不能造 cleaning、failed 等“已删除”进度。

建议把范围未解决项、清理项状态和证据完整性独立持久化，再按下表投影主状态，避免一个枚举抹掉并存事实。

| 判定次序 | 主状态 | 条件与必显信息 |
| --- | --- | --- |
| 1 | needs_scope | 仍有任何未解决范围；列待确认/暂停范围。清理可同时推进；失败项和重试原因必须同时显示。 |
| 2 | failed | 范围已全部解决，但至少一个必需清理项本次执行或核验已失败，且尚未进入有效重试；数据库删除回执保留，旧副本禁读。 |
| 3 | cleaning | 范围已全部解决，无已失败项，但仍有必需清理待处理/执行中/重启待对账。 |
| 4 | complete | 范围已全部解决，隔离事实已持久化，全部受管清理及安全读取状态均已确认成功，无未知或未确认项。 |

“范围已全部解决”指每项实际待确认义务已按 §2 冻结确认；可证明无关而排除的组另有证据依据，不冒充用户确认。用户确认只证明其选择，不能把历史来源完整性字段改写为“全球已知”。

### 4.1 转换条件

| 触发 | 原状态 | 结果 |
| --- | --- | --- |
| 部分范围确认提交 | needs_scope | 有剩余则仍 needs_scope；已确认成员隔离，剩余继续暂停。 |
| 最后一项范围确认提交 | needs_scope | 按清理事实进入 failed / cleaning / complete。 |
| 清理项失败 | cleaning | failed；needs_scope 时仍 needs_scope，并显式保留失败明细。 |
| 明确重试或启动恢复开始执行失败项 | failed | 仅将实际开始重试的项改为进行中；无其它失败项时 cleaning，否则仍 failed。不是点击即成功。 |
| 文件已经完成但进度提交中断 | 任一非 complete | 重启按相同任务身份验证实际输出，再确认完成；未核实前旧读口继续关闭。 |
| 所有项核实成功 | cleaning / failed | 范围也全部解决才 complete；还有未知范围仍 needs_scope。 |
| 发现新的受影响后继/受管投影/未知范围 | 任意，含 complete | 同事务传播限制并重新投影进度；只增加已知隔离且无需清理可仍 complete，有清理为 cleaning/failed，有新未决范围为 needs_scope。保留以前提交与当时完成观测。 |

complete 是本次已确认范围与当前证据下的完成事实，不是“以后永远不会发现新关联”的保证。晚到实际后继属于持续隔离义务；新发现的未知范围不能被旧 complete 放行，也不能借状态回退撤销数据库删除。仅状态、范围或清理进度发生可见变化时触发无正文失效通知。

## 5. 与已有验收和事务时序的关系

正常删除顺序：取得已有准入权限 → 校验重送/目标版本与必要证据 → 对受影响已产生 trace 通过非终结顺序屏障 → 同事务硬删行/FTS、登记无正文意图、隔离/暂停及 SQLite 投影/候选清除、成功回执 → 发布无正文失效 → 幂等文件清理及进度确认。

A54 屏障失败不执行删除。屏障不得调用现有会 seal/retire Run 的最终 flush；等待不占 FanOut 发布锁，也不把文件 IO 放入该锁。Run 最终 flush 与记录事务仍归原收尾所有者。

A28 负责已知闭包；A29 补上未知范围、确认与暂停；A30 保留人工历史和独立记录；A34 负责清理失败及恢复。新确认/晚到传播在 SQLite 内的隔离及投影失效同事务，不能用通知成功代替事务成功。

R13 的来源、目标或使用链受影响使整批候选 invalidated，清候选/差异并拒绝旧批准；仅因来源仍未知而暂停时，禁止读取或提交，不擅自把暂停称为已确认来源污染。真实批次状态接入归 #18。R14 的文件端口由 #45 独立验收，实际 Markdown 镜像由 #18 验收。

## 6. A29 展开验收摘要

每项从公共服务读取可观察结果，并在临时真实 SQLite 上运行；并发用 Event/barrier，时间用注入时钟。至少覆盖：

- A29-01–04：known_none/unknown 分名、部分及全部确认、确认与清理独立。
- A29-05–09：快照成员冻结、新 Run 不自动纳入、跨 Session、后继传播、无关组保留。
- A29-10–14：未知范围禁读与扩大、四类消费者、新输入聊天、人工历史保留。
- A29-15–19：迟到确认、并发确认、幂等重送、参数不一致/旧 key、提交回滚。
- A29-20–24：重启恢复、晚到证据、多操作叠加、非法范围/缺证、安全元数据与迟到读取失效。

#45 的注入端口 PASS 仅证明核心契约。#16/#18/#19/#46 仍分别完成真实消费者和最终浏览器路径验收。
