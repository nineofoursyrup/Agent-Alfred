## 第一轮：页面信息层级（已确认）

用户在收到以下四题的推荐后回复「全按推荐」，确认四页信息层级。原始答复及展示范围见 [APPROVAL.md](APPROVAL.md)。该确认不连带批准后续编辑或保存方式；下文保留推荐原意。

### Q1：Models 的首屏重心

问题：Models 首屏优先展示当前指派，还是先展示全部模型目录？

推荐：采用「指派摘要 → 按端点分组的紧凑模型列表 → 行内详情」。先显示主模型、辅助小模型及跟随主模型状态；端点头分开显示连接与目录状态，模型行保留钉选、支持态和指派标记。显示名、线路形状与覆盖价放入详情。

取舍：让日常使用者先确认实际指派，再展开目录挑选；全部候选及原有操作仍可到达。详情字段、价格依据、保存和冲突方式已由第二轮 Q5–Q7 确认。

### Q2：Connections 的分区

问题：模型端点、可选集成和 MCP 应平铺在一个列表，还是按来源类型分组？

推荐：按「模型端点／可选集成／MCP 服务器」分为三组。各项配置、连接与异常摘要常驻，只读地址、观测详情和维护操作就地展开；凭据重读、连接测试与 MCP 维护保留各自入口。

取舍：统一外观而保留不同接入的操作边界。MCP 启动许可与工具授权分开，工具授权仍归 Tools；不能为视觉整齐新增统一的“全部连接”动作。默认展开与异常定位已由第二轮 Q8 确认。

### Q3：用量账本的层级

问题：Ops 是汇总优先，还是进入页面就展示大量调用细节？

推荐：采用「筛选 → 分项汇总 → Run 表 → 页内账目明细」。精确金额、估算金额、费用未知次数与覆盖缺口分别可见；工具计量按服务和单位独立展示。Attempt、工具调用和历史正文逐层展开。

取舍：先看清本次账目的范围和完整程度，再定位具体记录。保持既有筛选、快照和 Run 链接语义；明细展开形式已由第二轮 Q9 确认，长内容与失效反馈按原合同整合。

### Q4：Database 的中央布局

问题：Database 是否保留参考稿的并排对象侧栏？

推荐：中央采用单列：上方可折叠的对象目录，中间 SQL 编辑器及执行／取消操作，下方独立结果区。目录与资源限制有常驻摘要；SQL 草稿、查询进度、结果是否收到、清理状态分别表达。

取舍：三栏壳层下避免再挤出一条侧栏，宽窄屏保持相同顺序；代价是查看完整对象目录时需展开。选择目录示例仍只填写 SQL，不自动执行；替换草稿和结果关联已由第二轮 Q10 确认，表格与状态沿既有约束整合。

### Q5：Models 的设置何时保存

问题：保留线路形状／覆盖价的“改动即提交”，还是统一为显式保存？

推荐：显示名、线路形状、各维覆盖价均按项显式保存；钉选和指派继续是独立动作。未保存、提交中、已保存及错误就地显示，收起详情保留草稿与提示。版本冲突保留草稿、展示当前值，用户核对后再提交；磁盘外改单独说明。

取舍：多一次明确的保存动作，换取一致且可预期的提交时机；沿用单项 mutation，不暗示存在全页或整行原子保存。读取当前值不得覆盖其他草稿。`external_change` 时当前读口仍返回内存 last-known-good，回读不能自行解决磁盘冲突或授权强制覆盖；当前缺少自动重新加载模型设置文件的受支持入口。

### Q6：价格编辑与实际计价依据放在哪里

问题：模型详情是否增加“当前有效报价预览”，还是分别呈现配置和实际账目依据？

推荐：Models 展示四维用户覆盖价及 `USD / 百万 Token`，明确“留空继续查价格链、0 表示该维零价”。实际单价、逐维 `price_source`、过期与阶梯价标记放在 Ops 的对应 Attempt 明细；本轮不新增报价预览接口。

取舍：现有 Models DTO 给的是 `price_override`，不能把候选来源 `sources` 冒充价格来源。Ops 已有价格链、冻结报价和实际费用分项，能说明本次计算采用什么依据。端点自报 exact 不生成估算分项，unknown 不显示金额，这些既有语义不再重新裁定。

### Q7：真实调用测试如何呈现

问题：推理探针如何让用户看清测试对象、费用提示与受理结果？

推荐：在模型详情内设独立测试区，按钮明确写“测试真实调用（可能计费）”，按已保存设置单次执行。就地显示提交中、已受理、明确拒绝或结果待核验；取得可信 Run 身份后提供运行详情入口，自动更新不得触发重复测试。

取舍：一次明确点击沿现有语义发起，不增加测试前的全页保存或隐式保存。待保存的线路／价格输入不自动纳入测试。HTTP 202 只表示受理，不能把它显示为调用成功；响应丢失且无法确认 Run 身份时不猜测绑定某条记录、不自动重发。Models 的探针结果不改写模型指派或凭空提高支持结论。

### Q8：Connections 的详情和维护按钮

问题：三组已确定，详细信息默认展开多少，维护动作放在哪里？

推荐：三组标题与逐项状态摘要常驻，详细信息默认收起，允许同时展开多项。页面顶部放“重新读取 .env”，MCP 组头放“应用 mcp.json”，各项的测试、重连、继续清理放在对应项；在途、失败、未生效与清理未完成状态不随折叠隐藏。

取舍：让异常和操作归属明确，减少完整诊断文本占用首屏。只读地址、凭据状态、观测依据／时间、目录健康、套餐用量、MCP 诊断按各类真实字段展示，不用统一占位成功填齐。展开不探测、不应用配置；异步更新不自动展开或抢焦点。

### Q9：Ops 的 Run 明细如何展开

问题：账目明细采用多层技术数据铺陈，还是明确划分可阅读的子区？

推荐：一次查看一条 Run，下面分为模型 Attempt 费用表、工具请求列表、历史正文阅读区。先呈现具名字段和状态，原始技术数据可再展开；历史正文保留三种查看入口及当前段范围，当次结果与后续核验分别标注。

取舍：不用原始 JSON 承担主要阅读任务，也不丢失现有技术明细。选择另一 Run 后清除原历史正文；财务明细仍使用同一账目快照，历史读取与当前核验继续各用自己的身份和失效规则。原始技术数据仅指现有安全 DTO，不扩大原文、密钥或任意文件读取能力。

### Q10：Database 的草稿与结果怎样避免混淆

问题：切换示例、查询中继续修改 SQL、复制结果时，如何保持操作对象明确？

推荐：折叠目录保留草稿；示例会覆盖已有编辑时先让用户选择保留或放弃。执行后再编辑 SQL 只影响下一次查询，现有结果明确对应已提交查询，并提示草稿是否已改变。“复制结果”明确标为“复制本页结果”，连同结果说明复制。

取舍：保留当前可编辑行为和执行参数快照，同时让用户分得清“正在写的 SQL”与“已执行的查询”。提交关联只在当前页面受管生命周期内存在，不建立查询历史或跨刷新 SQL／结果缓存。结果来源、覆盖、截断、读取时刻及清理异常仍按 Q4 保持可见，复制不是全量数据库导出。
