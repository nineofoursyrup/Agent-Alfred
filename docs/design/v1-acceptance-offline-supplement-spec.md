## Problem Statement

用户已经决定，发布验收不能让大量容易案例的高分掩盖一项关键任务失败，也不能仅凭 judge 的判分标签或合法引用就认定判断可靠。但现有机制没有可机械执行的关键义务门禁，没有与真实产品样本分开的裁判检验材料，也不能在新版材料及争议流程中准确表达“Agent 逐案复核，用户只审摘要和争议并作最终批准”。

因此，用户目前无法通过同一条可复核的公共路径，确认哪些任务必须全部满足、judge 是否漏判或依据不足、自己究竟批准了哪一版案例和哪些争议。手工填写批准字段、遗漏失败的摘要或旧批次的高分不能填补这些缺口。

## Solution

扩展现有验收证据机制，用同一套版本化合同覆盖材料准备、离线导入、独立复核、用户摘要批准、争议裁决、重读与报告：

- 在采样前明确关键义务和次要质量要求。关键义务与禁止项单独过关，次要质量按能力组、评分维度和适用案例计分。
- 为新校准及正式材料验证固定场景分布和来源隔离；把构造答案及正确对照作为独立裁判检验材料，不混入真实产品成绩。
- 向用户生成完整、可追溯的审核摘要与争议清单。Agent 意见、用户批准、运行授权是三种不同记录；不能互相替代。
- 保留原样本、原判分、分歧、更正链和首次失败。报告明确区分已证实失败、证据缺口与已满足条件。

本阶段以新临时证据库、合成批准来源、`ScriptedModel` 和 `MockTransport` 验证机制。缺真实材料、校准质量批准或通用数值门槛时，`v1_release` 继续 `BLOCKED`；已知失败与 blockers 并列保留，整体 `FAIL` 不被缺口隐藏。

## User Stories

1. 作为发布验收负责人，我希望预先标明每案的关键义务，并看到独立门禁结论，以免平均成绩掩盖核心任务失败。
2. 作为评测材料编制者，我希望校准、正式案例和裁判检验材料具有不同身份及覆盖规则，以免构造答案、浅改旧案或重复案例污染成绩。
3. 作为验收独立复核者，我希望先独立检查金标和判分依据，再与原意见对照，以便保留有证据支持的意见和所有实质分歧。
4. 作为用户，我希望只审包含全部失败、缺口和争议的摘要，并批准明确版本与案例范围，以便不逐案阅读全部材料也能保有最终决定权。
5. 作为后续执行者，我希望导入、重读、报告、裁决和校准引用执行一致的规则，以免换入口、换批次或补写时间后绕过门禁。
6. 作为历史证据的审阅者，我希望旧版本仍能按原合同解释，且新结论明确列出新增要求的缺口，以免旧记录被改写或自动升级为新版发布依据。

## Implementation Decisions

### R-01 版本边界与公共入口

新增显式 `schema_version=4`，合同身份为 `V1-ACCEPTANCE-OFFLINE-SUPPLEMENT-SPEC-r1`；不原地改变 schema1/2/3 的含义。新版本仍使用六组 `conversation`、`memory`、`tools`、`skills`、`routing`、`aggregation`，以及既有 `offline_fixture`、`calibration`、`formal` 阶段。

复用现有 schema 校验、`EvidenceStore.import_batch/read/revise`、纯 `report`、报告发布和 CLI。准备与离线演示入口须能显式选择新合同；旧调用保持原含义。判分、复核和裁决继续通过 `import-grades`、`import-reviews`、`adjudicate`、`adjudicate-reviews` 的对应公共路径追加，材料及批准可通过版本化批次导入或 revision 接口提交。无需新增平行证据库或另一套判分器。

新版本字段与关联对象必须使用闭合、版本化校验；未知版本、非法状态、重复身份、断链、哈希失配均不得静默忽略。缺必要材料的合法草案可以保存为待完成状态，但不能被解释为已有批准或完整证据。新版本的精确字段定义、示例和公共命令用法随实现交付，不新增任意 Python、路径或脚本执行能力。

### R-02 关键义务与次要质量要求

每案在采样前冻结具名义务，至少明确稳定身份、含义、所属既有评分维度、关键或次要类别、预声明适用性、预期行为及所需证据。完整覆盖任务的必要要求，不得用空关键义务清单逃避门禁；材料确无某类义务时须在金标和审核摘要中说明理由，由材料批准覆盖。类别及适用性进入材料、语义规则和批准的内容身份。

决定任务成立、事实足以支持决定或执行状态如实呈现的要求属于关键义务；纯文风、非必需解释及非必要排版可以属于次要质量。明确要求且为后续处理必要条件的格式属于关键义务。不得在看到结果后把失败义务降为次要或 N/A。

机械条件复用既有格式检查和真实公共执行证据；语义条件保留原 judge、独立复核及用户裁决的依据。引用存在、模型自述或复核者一致不自动证明语义成立，也不制造不存在的执行事实。

### R-03 门禁与计分

各义务保留通过、失败、不可判定和预声明不适用的逐项结果及依据。至少一项已证实关键义务失败，使新合同下的该候选质量结论 `FAIL`；其他案例或维度的高分不能抵消。关键义务必需证据缺失或待裁决形成 blocker，不直接冒充产品违规。禁止项延续零已确认违规要求，缺口同样阻塞。

按“能力组 × 评分维度 × 案例”计数：分母是预先声明适用的案例数；每案每维度最多贡献一次通过，该维度所有适用要求满足才进入分子。失败留在分母；未运行、缺有效判分和不可判定保留缺口，不移出分母、不计为通过；仅预声明 N/A 排除。逐项明细不得作为可任意增加的加分分母。

关键义务与禁止项门禁独立于次要质量的数值门槛。`aggregation_policy` 没有已批准数值时继续缺省为空，不预置 95%、90% 或允许失败数量。汇总政策不送给 judge；既有维度完成度、正确性及依据、适用的选择正确性保持区分。`offline_engineering`、产品 Run outcome、质量结论和 `v1_release` 不互相替代；任何 `PASS` 均须限定所判定的轴与合同版本。

失败场景按预先义务解释：工具或业务操作拒绝后，产品完成如实说明，可以满足“报告失败”的任务；若任务要求真实完成操作，诚实解释不能改写未完成事实。产品 Run 本身 failed/interrupted/max_steps、非法或空输出的既有失败规则不因场景标为“失败”而豁免，后续恢复也不回写首次结果。

### R-04 材料分布与隔离

为每个产品案例记录唯一的主要场景类别：正常、边界、失败或误导。新校准首版为六组各 5 案，每组 2/2/1，共 30 案；正式首版为六组各 20 案，每组 8/8/4，共 120 案。用冻结的预期清单验证每组数量和类别，不能靠给一案贴多个标签重复占槽，也不能在中止后缩减分母。小型 `offline_fixture` 明确为机制测试，不冒充完整校准或正式材料。

病例身份、实际内容、来源家族及来源谱系进入材料与批准绑定。正式案与校准、裁判检验、旧试跑及其他已见材料实质隔离；更名 ID、人物、数字或措辞不能自动成为独立来源。机械校验拒绝重复身份、已知同内容及已登记家族重叠；语义独立性由材料独立复核检查，未确认则阻塞，不能声称字符串标识能证明独立。

本票只实现清单、分布、绑定和审核机制及合成示例，不编制或批准真实 30/120 案金标。正式材料在校准和数值门槛批准后冻结；这些样本的通过率不宣称为日常使用成功概率。

### R-05 裁判检验材料与 judge 资格

裁判检验材料是单独标识、单独计数的证据集合，包含明确标注的构造答案、正确对照、任务/金标、预期判断、目标失效方式、来源及规则版本。预期判断须先经材料复核和用户摘要批准，不能由待测 judge 自己生成后自证。它们不得伪装产品 Run、Attempt 或真实结果，不计入 30/120 案产品分子分母，也不满足真实采样覆盖。

覆盖已经确认的独立失效方式：漏判已知禁止项违规、将正确答案误判为违规、接受不能支持结论的引用。原 judge 应只收到完成判分必需的材料；预期标签及原判分不能提前进入盲判上下文。保留原文、解析结果、实际引用、独立复核意见、比较及裁决链；不纠正引用、不裁剪输出、不自动补判择优。

标签一致性、引用结构有效性、语义支持性分别报告。必需判断依据不足是判分缺口；疑似违规和分歧待用户裁决。已确认的禁止项漏判使当前 judge 配置的校准资格失败，不能以总体一致率抵消，也不能通过改写产品成绩掩盖。普通分歧分组列出实际分子分母，准入数值仍待真实校准后批准。

记录裁判检验覆盖是否完整、所绑定 judge/协议/语义规则身份和批准状态；缺材料、身份漂移、未决争议或缺质量批准时不能宣告当前 judge 已校准。材料数量与未来调用规模在运行方案中单列；本票的合成正确/错误响应仅证明机制行为，不证明真实 judge 可靠。

### R-06 独立复核与角色

Agent 起草、材料/判分独立复核、用户最终决定分开记录。复用现有角色身份、盲标原件封存、输入输出哈希与时间顺序证据；至少存在与原起草或判分实例不同的内容复核实例。复核先在隔离上下文中形成并封存意见，再对照原意见，不能先看 judge 标签再倒填为盲判。

复核者允许使用与原 judge 相同的模型系列或供应商；不因缺少跨模型资源而阻塞，不增加未经选择的跨模型硬门禁。同模型一致不证明正确，仍须逐项依据和用户批准。此选择不取消产品模型与 judge 模型不同的既有要求。

复核身份、实际输入输出、起止时间及来源须可追溯；声明了独立角色但复用了同一实例、暴露了原标签、内容被改写或顺序不成立，不得作为独立复核证据。Agent 的复核或裁决建议即使名为 approved，也不能代替新合同要求的用户批准。

### R-07 审核摘要与用户批准

摘要由完整材料、逐案结果及复核记录生成，按六组展示：全部案例范围与内容身份、场景分布、关键义务、适用性和固定分母、全部失败/未运行/缺口、全部争议及状态、逐案原件入口、模型/规则版本和当前可作出的结论。用户只需审摘要与争议，不要求逐案打开全部材料。正文保持必要脱敏；若无法安全提供完整依据，显示缺口，不隐藏失败或假装已审。

摘要必须绑定其实际审核阶段和完整对象清单。材料摘要绑定案例、金标、来源、义务分类、语义规则和材料复核；采样后摘要另绑定首次结果、原判分、复核和争议链；校准质量批准及数值门槛批准各有其明确对象，不能借一个“全同意”覆盖尚未出现的结果。

用户批准事件至少绑定主体及可核验来源、明确决定、时间、摘要版本与哈希、对象类型、完整案例清单及对应内容身份。普通无争议项可随明确范围的摘要一并批准；摘要列出的未决项不会因为批准其余部分自动解除。新增案例或实质变更进入新版本，旧批准不自动扩张；不能删除未批准案以缩小批次。

将用户决定来源核验设计为可替换的独立只读接缝，沿用既有可信授权的来源与身份边界，区分材料决定和执行 grant。执行者填写的姓名、时间、布尔值、哈希、复制的确认文本或同权限 Agent 记录，都不足以自证用户事件真实。来源不可核验的记录可以作为待确认材料保留，但不能产生有效批准。生产未配置可信来源时 fail closed；离线正向仅用明确标识的合成来源，不承诺本票已经接通真人认证服务。

材料/摘要批准不授予模型调用、费用、部署或发布权限。任何测试批准都不能转成真实批准；任何用户质量批准都不能替代独立执行授权、可信 Dispatch 和硬金额上限。

### R-08 争议裁决与时间顺序

起草与复核意见不同、原判分与复核不同、疑似禁止项违规、关键义务性质不清或依据不足，必须显式形成争议，保留原意见和证据。原始争议不能在后续达成一致时从历史摘要中消失。Agent 可提出处理建议，最终解决须有可核验的用户决定，精确绑定争议、目标案例/原判分/规则、依据及结果。

支持确认违规、依据充分地否定原疑点、证据不足仍待定；维持既有等价语义。有效裁决只追加有效结论，不改原 judge 字节或首次执行事实。证据不足不自动判产品违规；确认的执行失败也不能被无依据的文字批准改成成功。若裁决发现规则或材料必须实质修订，形成新版本并按依赖失效，不追溯降低旧案义务。

材料、义务分类、语义规则与事先冻结的裁判预期判断，须在相应执行起点前批准。采样后的结果复核和争议裁决须绑定已存在的原结果，不能倒填为事前材料批准。正式批引用的校准质量批准及通用阈值批准必须先于正式执行，阈值批准不得早于所引用校准批准。

沿用带时区时刻、允许合法等时、原共享预算起点与最早采样形成的原始时间上界；补判、regrade、新报告和子批次不刷新继承样本起点与七天时效。导入、重读、正式引用和执行预检都应用同一时间与来源规则，不能只在一次 preflight 检查。

### R-09 历史兼容、派生与报告

旧 schema1/2/3 的原字节、批准角色含义、判分和解释保持不变；不能把旧 `agent_approved` 重贴为新版用户批准，不能仅修改版本或 contract 字符串生成新版有效包。旧包继续可按其版本读取及解释，当前时效等原有动态条件仍照常计算。

新版报告必须明确合同、候选、批次及各轴状态，展示关键义务门禁、案例计数、裁判检验、独立复核、用户批准和未决争议。引用旧材料须明示历史用途与新版未覆盖项；旧通过结论不证明新增门禁已满足，旧校准也不自动满足新协议/规则。缺少新版批准或来源时不能发布新版 PASS。

已有 `regrade/revise` 继续保留原输入、首次产品结果、请求史与原采样时间；变更金标、义务类别、语义规则或 judge 身份使对应批准、判分或校准资格按其依赖失效。旧结论留作历史，不跨批挑最好结果。普通报告修订不重置预算、不自动重跑。无需提供历史库的就地升级或一键追认。

复用既有不可覆盖批次、新报告与明确 latest 身份。纯读核验不写库；CLI `report/verify` 等现有报告发布行为须继续如实说明。验证与文档示例使用全新输出目录，禁止向受保护历史证据库写入。

### R-10 离线边界与交付

本票只交付机制、合成夹具、公共路径证明及使用文档；不调用真实模型、不读取真实凭据、不部署云资源、不写生产业务数据。正向网络接缝只使用既有合成 Authority/Dispatch 与 `MockTransport`，产品模型使用既有离线替身；真实执行缺可信来源必须在凭据读取及工厂构造前拒绝。

沿用单套冻结产品配置、完整六组、不跨配置择优及可验证硬金额上限要求。当前不挑选真实模型 ID，不填写真实额度，不启用 unknown 金额接受模式，不扩大产品 wire/端点或模型指派能力。

新输出包括可校验的 schema4 示例、各公共入口的离线使用说明、用户摘要及争议示例、旧版兼容说明和本规格验收证据。实现完毕只可声称离线机制通过；真实环境隔离、材料质量、judge 质量、在线许可和 v1 发布状态分别列出。

### 关键反例

下列反例描述独立失效方式，允许与同一行为测试的相关 AC 合并，不要求一行一个新测试。

| ID / 来源 | 前置与操作序列 | 预期、恢复与验证 |
|---|---|---|
| CE-01 / Q16、Q20 | 其他案例全过、某案关键义务失败；增加次要通过条目，再试将关键项改为 N/A 或降低严重性。 | 失败不被稀释；修改材料失去旧批准。通过 import → report → read 证明；恢复为原声明或创建新未批准版本，不能改旧案。 |
| CE-02 / Q18、Q22 | Agent 有材料复核意见；填写 human 姓名/时间、复制一句确认或把 agent_approved 改名，向新版公共裁决/材料入口提交。 | 缺独立可核验用户来源时不生效；真实调用工厂保持未触达。仅合成 Authority 签发的精确测试事件可用于离线正向，不能追认真实用户。 |
| CE-03 / Q22 | 摘要获合成范围批准后，删掉失败/争议行、换案例正文或新增未批准案例；保留旧摘要 ID 和批准记录。 | 摘要或清单绑定失配，不能缩分母/继承批准。以新摘要及新决定恢复，旧包和原争议保持；验证重启后的公共重读及报告。 |
| CE-04 / Q24 | 同模型两个实例先各自独立判分；对照允许该正向；再复用原 judge 实例、提前输入原标签或修改已封存盲标输出。 | 相同模型不被误拒绝；伪独立或字节/顺序失配无效。新建真实隔离的复核记录可恢复，旧记录保留；由公共复核导入与报告观察。 |
| CE-05 / Q17、Q21 | 已知错误答案被 judge 判过或引用无语义支持；将构造答案登记为产品 result 或计入30案分母。 | 分别记录漏判/支持性缺口，不能靠总体一致率抵消；材料类型混用拒绝，产品计数不增加。修订规则需新身份和待批准状态，原 judge 不改。 |

### 复用接缝与必要检查

- 复用现有 schema3 身份/策略、案例分数、争议持久化、人工裁决、Agent 角色与盲标时序、材料/校准/汇总批准截止、历史隔离、预算准入及基础设施停机测试；旧版用例保留其原版本语义。新增覆盖集中于 AC 中新版关键义务、裁判材料、用户摘要批准及跨入口失效方式。
- 通过 `EvidenceStore` 公共导入/重读/revise、纯报告和 CLI 子进程建立新行为证据；真实 Host/SQLite/Registry 路径继续承担执行事实。替换外部模型和可信来源边界，不把全部内部业务流程替换成手工字典。
- 用新隔离库验证完整合成正向以及必要反例；同一用例可证明多个相关 AC。测试用分数和批准须明确为 synthetic/test，不能生成可复用的真实质量结论。不要为纯文案或镜像字段重复建立测试。
- 由于修改共享证据 schema、判分及批准边界，实现交付须完成当前项目 CI：Ruff、Skill 校验、`.env.example` 一致性、完整离线确定性测试、wheel/sdist 构建及 base/mcp 干净安装、Dashboard typecheck 与离线 browser 检查。Ubuntu CI 使用 CPython 3.14；macOS 安装公共路径须使用具备共享 SQLite C API 的 CPython 3.14。环境未执行的检查列为 NOT RUN，不能用另一平台代替。
- 已通过且代码、输入、依赖和环境仍适用的检查直接复用；只因有关改动、新失败或未覆盖风险再跑。新门禁、browser 输出、报告和临时状态均写入新隔离目录，不覆盖旧证据或截图。CLI `report/verify` 会写报告，不能拿其名称当作只读保证；保护历史库时用纯读并比较前后清单、内容和 latest。
- 本次规格发布只做文本、交叉引用、范围/AC/反例一致性及远端读回检查；产品测试和实现验收均 NOT RUN，不以规格发布代替实现证据。

- 真实产品/judge 调用、30 案真实校准、120 案正式验收、真实金标编制及质量批准。

- 改变产品对话/工具/workflow 行为、增加模型 wire 或业务指派位、Dashboard 设计迁移或通用后台审批 UI。
- Git 提交、推送、合并、发布及关闭 #83。施工票 ready 不等于已实施或已获在线执行授权。
