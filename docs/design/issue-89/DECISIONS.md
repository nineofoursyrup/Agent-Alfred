## 第一轮：已确认的方向

用户在收到下列 Q1–Q6 及对应推荐后回复「全按建议」。本节保留当轮推荐原意，下文「建议」均已确认；其中明确留待后续的细节并未提前获批。

### Q1：中央区如何承载列表与详情

事实：宽屏三栏下，1280px 视口的中央区为 728px，1100px 时仅 548px。原参考的 Loop 在中央再次横分列表与明细；正式壳层还需容纳右侧唯一 MainBar。

建议：收件箱与运行都使用中央区的「列表 → 详情」路径。点击条目后详情占中央区，保留明确返回。收件箱会话详情默认显示只读消息预览，并可切换「本会话运行」；新建与继续保持显式操作。预览入口不改变 MainBar 所选 Session。

本轮确认范围：首版采用这一中央布局与预览分区。URL、分页恢复与精确焦点规则留待下一轮细化。

### Q2：运行列表的可见信息

建议：紧凑表格展示用途、请求摘要、入口／受理时间、短 Run ID、阶段／结局和独立记录状态。仅已获准聊天显示已有的脱敏请求摘要；系统用途以类型和 ID 识别；准入待定、未获准或无法确认时不展示输入摘要。详情继续承载正文、费用细目及过程。

沿用默认全部及现有筛选参数；聚合的分组口径由 Q3 单独裁定。窄屏可重排字段或让表格局部滚动，不能裁掉结局、记录状态与准入缺口。记录状态缺乏可信证据时显示未知。

本轮确认范围：正式运行列表加入有明确披露边界的请求摘要及上述首屏字段。其所需只读补充将在后续规格中明确，不能宣称当前接口已经满足。

### Q3：手动聚合的筛选归属

事实：已批准的聚合合同要求独立 `purpose=aggregation`、关联 Session 并支持人工会话展示；现有列表 SQL 将其纳入 `chat` 筛选，而部分实时／定位代码归入 system。不能用其中一个实现细节代替统一的产品口径。

建议：中文筛选为「全部／会话运行／系统运行」，保留旧 `all` / `chat` / `system` query 值。「会话运行」包含普通聊天和手动聚合，但每条用途分别标明；系统运行保留 probe、consolidation 及未知用途。列表、当前槽、深链接定位与收件箱使用一致归属。聚合仍不是普通 chat，也不进入自动工作窗口／聚合窗口／提炼来源。

该选择独立于 Q2 的摘要策略：若同时采用 Q2，仅 admitted chat 显示脱敏请求摘要；聚合以独立用途与 Run ID 识别，不据此扩展目标／草稿披露。

### Q4：运行详情的信息层级

建议：以「Run 摘要 → Step / Attempt 过程」为主线。失败、中断、未保存和过程缺口常驻清楚可见；输入／检索、分流、聚合、Graph 单次路径、用量与 trace 导出按独立分组展开。所有现有证据入口逐项映射保留。

正文与密集字段的默认展开、只剩账目而无过程时的布局、各分组的刷新及失效处理，在此层级确认后细化。Graph 继续是带身份和时间的手动快照，不由展开分组改为自动执行或自动重放。

### Q5：返回来源与定位正式回复

建议：从运行列表、收件箱预览或 Overview 进入详情后，「返回」恢复对应来源及适用的筛选／位置；直接打开 Run 深链接而没有站内来源时回运行列表。

关联 Session 且有可读回复／聚合草稿的 Run 提供明确的主对话入口。同一 Session 可「在主对话中查看回复」；其他 Session 明示「切换到此会话并查看回复」，只在用户点击后走既有切换守卫并保留原草稿。聚合入口按实际内容称为草稿，运行详情仍不复制正式回答。

本轮确认补齐精确回复定位能力。现有继续操作只有 Session 级语义，尚不支持精确 Run 定位；没有正式回复、无 Run 的旧消息、正文失效及目标在更早分页中的边界，留待下一轮细化。

### Q6：新数据到来时是否改变列表

建议：当前运行槽与正在查看的过程沿用既有 Stream 更新；历史列表保持当前阅读位置，新终态到来提示「有新运行，刷新查看」，由用户显式刷新。会话、消息与运行的分页继续各自独立，不因新数据到来把用户送回第一页。

历史详情和 Graph 快照保留明确读取／刷新入口。只读恢复不触发重新执行或保存重试；不以额外轮询连接或图动画暗示持续更新。

本轮确认历史列表采用稳定阅读＋显式刷新；具体何时失效、可保留哪些旧内容以及恢复失败状态，留待下一轮裁定。

## 第二轮：Q7–Q11 已确认

用户在收到 Q7–Q11 及对应推荐后再次回复「全按建议」。下列「建议」均已确认；第一轮后的设计树仅保留为访谈过程记录，其问题已在本轮解决。

### Q7：预览、返回和刷新恢复到哪里

建议：会话只读预览及「消息／本会话运行」分区进入 URL，允许收藏、直接打开及刷新恢复对象和分区；这些动作仍不选择 MainBar Session。同文档返回时重新核验并恢复来源的筛选、原条目和阅读位置；来源对象失效时明确说明，回到相应列表。

整页刷新只承诺恢复 URL 指定的对象和分区，不承诺重建此前加载的全部分页或展开状态。会话消息、会话 Run、总 Run 列表各自使用原有游标；返回所需身份、锚点和非正文呈现信息不保存成正文缓存。直接打开没有站内来源的 Run 仍回运行列表，沿用已确认 Q5。

建议的地址细化为 `/inbox?session_id=<opaque-id>&view=messages|runs`；缺少参数与合法空 ID 区分。具体编码使用现有 URL 设施，旧 `/inbox` 与所有既有 Run 深链接继续有效。

### Q8：如何定位很早的回复，以及定位失败如何退出

建议：在同一 MainBar 中按精确 Session/Run 定位对应记录，显示「已定位历史回复／草稿」及「回到最新」；读取有界的定位记录，不要求逐页扫描整段会话。普通消息分页仍保留原身份和游标；定位记录与普通历史中同一 Run 合并，不出现第二份正式回复。

现有 `/api/reply` 已支持精确完整正文，但没有历史位置及用户消息对的定位协议；后续实施需要补充有界的定位元数据／记录读取，并复用正文恢复的内容和保护边界。“有界”限制定位记录数量，不擅自截断既有完整正文契约。

仅显式点击已确认 Q5 的动作可切 Session；切换限制、原草稿保留和异步焦点规则沿用 #87。定位到历史位置时新回复不抢走阅读位置，继续显示回到最新入口。

未保存但同进程仍可读取的回复允许定位，保留未保存标记；读取失败保留明确状态及只读重试。无回复、保护边界扣留或旧实例未保存正文不可恢复时说明实际原因，不从 trace 补造，不自动改为其他 Run。没有 Run 身份的旧消息仍在会话预览／普通历史中可读，不伪造精确 Run 定位。

### Q9：过程和长内容默认展开到什么程度

建议：所有可证明的 Step 摘要始终可见，当前步骤及有失败／缺口的步骤默认展开状态说明；Attempt 明细与过程正文按需展开，作废正文默认收起。异常简述和缺口徽标不藏进折叠区。

长文本先显示最多六行，并明确提供「展开全文／收起」；完整文本始终可达。请求摘要最多两行，缺少摘要时明确说明或使用既定类型／ID，不补造内容。关键状态和错误原因可换行，不能用省略号隐藏；代码、表格与图示使用有名称、键盘可进入的局部滚动区域。

用户手动改变展开状态后，普通事件更新保留其选择。Graph 的 Step/Attempt 链接等显式定位操作可展开相应容器并移动焦点；自动数据更新不抢焦点、不跳动阅读锚点。Step 摘要不重复放置与 Attempt 相同的整段过程文本；正式回复仍由 MainBar 负责。

### Q10：局部失败、旧数据和过期如何呈现

建议：列表、会话预览各分区、Run 摘要和各证据区独立标明读取状态与时间，可分别重试；一处失败不清空其他仍有效的结果。首次读取失败与确实为空分开。普通网络失败可保留仍允许显示的旧内容，明确标为旧快照／离线，并给出重试；未知不能变成零、已保存或正常结束。

普通列表／预览／Run 详情的 HTTP 读取超过十五分钟未核验时提示「待刷新」，不自动重跑读取或改变 Run 结局。新数据通知、来源身份变化或更严格的既有失效条件优先于时间阈值。壳层当前运行和实时过程继续遵循 SSE 身份及连接事实，不套用历史快照的新鲜度来推断运行状态。

Graph 继续沿其明确手动快照与旧快照规则，记忆当前引用、账本 snapshot 与导出任务保留各自更严格的撤销／失效／过期规则；不能为统一样式而保留已禁止显示的正文或复活旧下载。新实例下重新核验普通页面来源，拒绝旧请求回写；Graph 可按原合同明确标示上一实例快照。

第一轮的显式刷新只约束列表和普通详情读取，不取消用户主动创建导出后的既有任务状态查询，也不暂停 MemorySync 等已存在的保护核验。

### Q11：窄屏和拥挤中央区的列表形式

建议：按中央内容区可用宽度适配。达到 680 CSS px 时使用紧凑表格，不足时改为每条记录纵向排列的字段卡；两种形态保留相同信息、顺序、操作和状态，不依靠横向滚动寻找结局或未保存提示。

这个阈值独立于 #87 的 1100px 壳层断点：宽屏三栏中中央拥挤时也可以使用字段卡。详情维持单列，局部代码／证据表格／Graph 仍可按原合同局部滚动。

会话和 Run 的主要入口使用真实链接／按钮；视觉重排不改变合理的键盘顺序或丢失焦点。沿用 #86／#87 的字号、焦点、减少动效、宽窄视口与文字放大验收，不重新引入小字压缩。
