# 状态补丁自带 `state_revision`，不占事件 `seq`

SSE 上要送两类根本不同的东西：**发生过什么**（领域事件）与**现在是什么样**
（生命周期快照）。把快照补丁塞进事件通道、顺手领一个 `seq`，是最省事的做法，
也是错的。

`seq` 是**发布线性化顺序**（[ADR-0015](0015-events-prepared-outside-the-lock.md)），
而且是**所有连接共享的同一个编号空间**。多发一个号，别的连接就凭空缺一个号——
而「缺号」恰恰是重放环判断「漏了东西」的依据。为一条连接服务的东西去消耗
全局编号，等于让 A 的传输细节去污染 B 的完整性判据。

于是 SSE 顶层闭合成三类载荷：`domain_event` 用 `seq`；
`transport_notice` 与 `state_patch` 都**不占** `seq`，
后者另带 `process_instance_id` 与自己的 `state_revision`。

## Consequences

系统里从此有**三个单调递增的整数**同时存在——`seq`、`state_revision`、
`activity_revision`——且**互不相通**。任何一处拿其中之一给另一个排序、
或从其中之一推断另一个新旧的代码，都是错的。这是这条决定难以逆转的那一面：
只要有一处混用，症状会以「偶发的顺序错乱」形式出现在离现场很远的地方。

补丁是**绝对替换**而非增量，因此正确性只由「原子快照 + 单调 revision」保证，
不由送达顺序保证。服务端必须**先更新权威快照、再投递补丁**；
投递一旦不可靠就直接断开，让客户端重连去取一份原子快照。
