# 记忆检索不向调用方暴露可比较的相关度分数

`SemanticStore` / `EpisodicStore` 的 `search()` 返回**按相关度降序的有序列表**，
不返回任何可参与比较的数值。需要展示时，Store 可以给一个不透明的 `relevance: str | None`
（如 `"bm25 -3.21"`），契约只有一条：**不得参与任何比较或阈值判断**。

理由是三种后端的分数尺度互不相通且方向相反：SQLite FTS5 的 `bm25()` 返回
**负数、越小越相关**；余弦相似度是 `0..1`、**越大越相关**；托管后端各有各的标度。
只要 Protocol 里放一个 `score: float`，调用方迟早会写 `if score > 0.7`——
而换 Store 那天它**不会报错**，只会静默地永远返回空、或永远全放行。
归一化到 `0..1` 同样否掉：那是凭空造一个看着可比的数，
与我们废除「未知 Provider 默认 $3 / $15」是同一类问题。

配套的一条契约不能省：**`search()` 只返回后端自己判定相关的条目，
结果可以少于 `limit`，可以为空。**FTS5 的 `MATCH` 天然只回匹配项，
而向量后端默认会**永远凑满 k 个**，哪怕全是垃圾。
「够不够相关」的判断必须留在 Store 内部——只有它知道自己的分数尺度。

## Consequences

「为什么 `search` 不返回 score」会是每个后来者的第一个问题，因此记在这里。
加回一个 `score: float` 很容易，但等下游写完阈值判断之后再拿掉就极难，
这是本决策难以逆转的那一面。

相应地，一致性测试**自己也不许对 `relevance` 做数值断言**——
测试要示范这条契约，而不只是描述它。跨 Store 的排序断言改用
**固定且无歧义的语料**（相关项与明显无关项各若干），
断言「相关的都在、无关的一个都不在、顺序符合语料的设计」。

另有一条与本决策同源的 fail-closed 要求：**存储故障不得伪装成空结果**。
在本决策之下 `search` 返回空是完全正常的语义（「没有相关记忆」），
而磁盘或远端故障若也返回空，两者在界面上长得一模一样。故障必须抛出，不得吞成空列表。
