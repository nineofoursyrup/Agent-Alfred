# 事件在锁外无副作用准备，在短临界区线性化并获得 seq

[ADR-0004](0004-flush-barrier-at-run-end.md) 把 IO 赶出了发射路径，
但留下了一件重活在临界区里：**序列化**。TraceSink 要生成 JSONL 行，
SSESink 要生成线格式帧，CLI 要格式化字符串。#3 §7 定的
"`emit` 必须 O(1) 非阻塞"其实一直在要求"别在 emit 里做重活"，
而序列化正是重活——此前 SSE 靠"把序列化推后到 dispatcher"绕开了它，
直到重放环要求"可重放帧必须先原子入环、再投递队列"把那条路堵死：
先排队后入环，会让所谓的权威恢复源在拥塞时恰好失去权威性。

把序列化移到临界区外，天真的做法是让各线程自行序列化后再去抢锁——但那样
`seq=8` 会因为正常的线程调度先于 `seq=7` 到达下游，而这**不是不变量违例，是误杀**。

因此把发射拆成两阶段：

- **准备（锁外）**：脱敏后的规范序列化、UTF-8 安全切分、物理帧预构造。
  必须是纯函数：无 IO、无共享副作用、可并发、允许慢。
- **提交（短临界区内）**：`FanOutSink` 分配 `seq`、构造唯一的 `SequencedEvent`、
  依次调用各 Sink 的提交。提交只做**定量**的引用入队、环更新或状态切换，
  不得按载荷大小复制数据、不得阻塞、不得写 IO。

`seq` 由此获得精确定义：**发布线性化顺序**——所有 Sink 完成准备后进入
临界区的次序，**不是**业务线程开始发事件的时间顺序。
三个消费者因此看到完全相同的顺序，而顺序由分配 `seq` 的那一把锁保证，
不靠任何下游校验。

## Consequences

`EventSink` Protocol 由单个 `emit` 改为准备 / 提交两阶段，
每一个 Sink 实现都要跟着改——这是这条决定难以逆转的那一面。
方法叫什么名字不是（`prepare` / `commit` 只是当下的命名）。

`Event` 分裂成两段冻结类型：准备阶段收 `UnsequencedEvent`，
提交阶段构造 `SequencedEvent`。不让 `seq` 变成回填的可变字段——
frozen 破例一次，之后每个读代码的人都会默认整个事件是可变的。

"进程内全局单调"从此不可读作因果先后。并行工具批下两个工具的
`tool.started` 谁的 `seq` 小，反映的是谁先完成准备并抢到锁，
而不是谁先开始执行。任何从 `seq` 推断业务时序的断言都是错的。
