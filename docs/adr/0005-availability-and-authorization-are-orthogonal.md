# 工具的可用性与授权是两个正交维度

「有外部副作用的能力默认关闭」直觉上是一个开关：一个 `enabled: bool`，或者工具上一个
`requires_opt_in` 标志。我们拆成两个互不替代的维度：**可用性**（密钥与依赖配齐了没有，
外在表现是连接四态）与**授权**（用户准不准它动外部世界，三态 `unset` / `allowed` / `denied`）。
只有可用且已授权的 `external` 工具才可执行；本地工具不进授权维度。

拆开的理由是这两者**不是同一个事实**：密钥齐备而用户不准，与用户想用却没配密钥，
是两种相反的处境，需要两种相反的界面提示与两种相反的下一步动作。合并成一个布尔值之后，
「为什么这个工具用不了」这个问题就再也答不准了。

授权状态因此存在**用户配置**里，而不在 `Tool` 上。`Tool` 是代码里的静态声明；
把运行时权限放进同一个 dataclass，会让「改代码来开权限」变成一条可用的操作路径。
工具上只留 `effect`（`local_read` / `local_write` / `external`）这一个静态声明，
「需不需要授权」由它推导——两个字段表达同一件事，就有了不一致的机会。

## Consequences

暴露矩阵出现一处**刻意的不对称**，不知情的读者会当成 bug：
`未配置 + unset` **暴露**引导 Schema，`已配置 + unset` **隐藏**。
判据是「用户是否表达过不要用它」——未配置是意外，指引有价值，模型能告诉用户去配 key；
已配置则只差用户的意志，模型不该反复试探。

由此产生第二件反直觉的事：未配置的工具**仍然出现在工具列表里且可被调用**，
只是返回 `configuration_required`。这与「默认关闭」的字面读法冲突，但保住了
「模型能解释自己为什么做不到」这条更重要的性质。为了不让它在暗示自己能跑，
引导 Schema 必须**参数置空**并在描述里如实写明不会执行——
一份与真实 Schema 一模一样的声明就是在伪造能力。

代价是配置界面必须同时渲染两个维度，且改授权落在「重建 Agent」这一档重载范围。
