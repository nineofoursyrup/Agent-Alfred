# 中央 fail-closed Redactor 位于 FanOutSink 入口

四个事件消费者里，只有 trace 与 telemetry 落盘，直觉上脱敏该放在这两个写入点。
我们放在更上游：`FanOutSink.emit` 的入口，脱敏一次，所有 Sink 拿到的都是已脱敏事件。

理由是消费者名单会长。Dashboard 的 SSE 即使只发到 localhost 也是**离开进程的 HTTP 流**，
浏览器会把它写进自己的缓存与 devtools 历史；CLI 的输出会被用户复制进 issue。
把脱敏钉在唯一的收敛点上，「哪些 Sink 需要脱敏」这个问题就不再需要每加一个消费者回答一次。

匹配依据必须两条并用：敏感**字段名**黑名单，加上**已加载的密钥值集合**做值匹配
（只纳入达到安全长度的值，短值会大面积误伤）。只有字段名黑名单是纸糊的——
`web_search` 抓回的网页正文里出现的密钥，不在任何黑名单字段里。

**失败模式是 fail-closed**：遇未知结构或匹配异常时替换整个受影响载荷，
并发出一条不携带原文、固定内容、绕过递归脱敏的 `redaction_failed` 通知。

## Consequences

其余各层从此可以假定自己永远见不到密钥，而这个假定一旦散布开就很难收回——
这是本决策最难反悔的部分。

代价是脱敏跑在业务线程上（临界区之外，`Redactor` 无状态可并发），
且 CLI 与 SSE 也付了这份开销，尽管它们不落盘。这是有意的：
fail-open 的脱敏器等于没有脱敏器，而它恰好会在最不设防的那次异常里泄漏。
