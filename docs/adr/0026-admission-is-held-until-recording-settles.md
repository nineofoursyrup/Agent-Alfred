# 准入租约持有到记录落定

Run 已经产出回复、收尾事务还没落定时，「谁占着准入」这个问题有两个子情形，
一开始只答了第二个。

## `pending`：租约不释放

`run.finished` 发布的那一刻，很自然会想把 Run 当作结束了、放行下一个。
不行——那一刻**唯一的未记录终态投影还攥在它手里**，而那份投影是有界单槽。
放行下一个 Run，它跑完时会覆盖同一个槽，第一条回复就此无声消失，
而「不得覆盖」原本只是一句没有执行路径的愿望。

因此 `run.finished` **只把协调器推进到 `recording_pending`**，
租约要等事务得出 `recorded` 或 `failed` 才释放。期间的第二次提交
返回**现有的 `409 run_in_progress`**——不新增错误码，因为这确实就是
「上一个还没完」，只是「完」的定义延伸到了落盘。

## `failed`：关闭准入

写不进去时有三条路：照常接活（同上，覆盖投影）、把未记录终态排队攒着
（无界，且攒的仍是最不该丢的东西，只是把消失推迟到内存耗尽）、或者拒绝。

选拒绝：保留该投影并以 `503 recording_unavailable` 拒绝新 Run，
直到记录恢复或进程重启。这是
[ADR-0016](0016-concurrent-mutation-returns-409.md)「409 绝不排队」
在记录侧的同一条原则——**说不出真话的时候就明说做不了**，
不要维持一个看起来还在正常工作的系统。

## 两处次序不可交换

- 提交成功：**先**把权威快照更新为 `recorded`，**再**释放租约。
  反过来，下一个 Run 会在快照仍写着旧终态时被准入。
- 提交失败：**先**进入 `recording_failed` 并保留投影，**再**开始返回 503。
  反过来，是对外宣告一件内部还没成立的事。

状态机由此可执行：`idle → accepted → running → recording_pending → idle | recording_failed`。

## Consequences

一次写盘故障会让助手**整体停止接单**，而不是继续聊、悄悄丢历史。
对一个单用户本地系统来说这是对的取舍——这里没有别的副本能事后补上这段对话。

租约多持有的这一段是**可观测的**：用户会在忙态卡上看到「正在保存」。
这比让他发出第二条消息、再在某处悄悄丢掉第一条要好。
