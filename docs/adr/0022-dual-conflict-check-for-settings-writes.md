# 设置写入用双重冲突判据

模型设置（钉选与指派）持久化在状态目录下的一份文件里，而它有两类互不重叠的并发来源：
**多个浏览器标签页**（都在同一个 `RuntimeHost` 里、都守规矩，但可能各自拿着旧快照），
以及**进程外的编辑**（不走我们的锁，可能是手改、同步盘、备份还原）。
一道检查挡不住两类，因此保留两道：

1. 浏览器发来的 mutation 必须携带 **`expected_revision`**，与 `RuntimeHost`
   内存中的当前 `revision` 比对，挡住陈旧标签页的覆盖写。
2. `ModelSettingsStore` 另将**加载时**记下的 `{exists, sha256(raw_bytes)}`
   与**写前**重读的磁盘状态比对，发现进程外改动。

任一不符即 `settings_conflict`，分因 `stale_revision` / `external_change`，
**一个字节不写**。`revision` 每次成功写入单调加一，用于界面与诊断；摘要只在内部使用。

只留 `revision` 不够：手改文件的人**不会记得把它加一**，而那恰恰是第二道要防的人。
只留摘要也不够：两个标签页的写都经由本进程、都会更新摘要，磁盘从头到尾自洽，
第二道什么也发现不了。

落盘顺序同样是这条决定的一部分：同目录独占创建临时文件 → 强制 `0600` →
写入并 `fsync` → 再次（缩小窗口地）核对目标 → 原子 `rename` → `fsync` 父目录 →
**而后**才发布新的内存快照与摘要。先发布内存快照再落盘，会让一次失败的写留下
一个磁盘上不存在的「已生效」设置。

## Consequences

**这份文件不是受支持的人工编辑接口。** 摘要比较只对不守本系统锁的外部编辑提供**乐观**
检测，消灭不了「最终核对与 rename 之间」的文件系统竞态。它的作用是让手改**大概率被发现并拒绝**，
不是让手改成为一条可用的操作路径——唯一的模型入口仍然是 Dashboard 设置页。

启动期读到语法错误、引用破坏或**更新版本写下的 schema** 时，一律保留原文件、
进入 `settings_invalid` / `settings_schema_newer`，**禁止聊天也禁止写回**：
用旧 schema 写回，会把新版本的字段静静抹掉。
