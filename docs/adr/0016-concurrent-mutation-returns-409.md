# 并发 mutation 立即返回 409，绝不排队

CLI 与 Dashboard 共用一个 `RunCoordinator`，任意时刻至多一个 Run 在执行，
所有会修改记忆、设置或外部状态的端点也走同一个 mutation gate。
这一半由 [ADR-0001](0001-model-client-fully-synchronous.md) 的"副作用一律串行"
与 [ADR-0010](0010-wave-snapshot-and-single-writer.md) 的全局单写者推出。

但那两条只规定了**谁可以执行**，并没有规定**冲突的请求该怎么办**——
而**队列本身也是串行的**，排队与全同步、全局单写者三者完全相容。
"拒绝而非等待"是一个独立且欠定的决定，必须单独记下来。

选择**立即返回 409 并附机器可读原因，不排队**。

排队看起来只是"多等一会儿"，实际会一次性引入五组新语义：队列的持久性
（进程重启后那条排队的消息还算数吗）、取消（用户改主意了怎么撤）、
超时（排了十分钟还要跑吗）、公平性（CLI 与浏览器谁优先）、
以及幂等（用户以为没发出去，又点了一次）。每一组都要有答案，
而单用户假设下"两个 Run 同时想跑"几乎总是误操作——
为一次误操作付这五笔设计成本不划算，如实报错比悄悄排队诚实。

## Consequences

这是本地图里少数几条**最终用户能直接撞到**的决定：在 Dashboard 上发消息时，
若 CLI 那边正在跑，界面会立刻收到拒绝而不是转圈等待。界面必须如实呈现
"正忙"以及正忙于什么，不得把 409 渲染成一次失败。

HTTP handler 线程**不得自己执行 Run**。`RunCoordinator.submit()` 接受后
返回 `202` 与 `run_id`，交给唯一的执行线程，过程与结果统一走 SSE。
否则一个两分钟的 Run 会把 HTTP 请求挂两分钟，浏览器自己先超时。

改成排队难以逆转：上面那五组语义一旦进入协议与界面，就再也退不回来了。
