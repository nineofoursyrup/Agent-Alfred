# 裁剪是独立的生命周期事实，不改写观测

保留策略删掉一个 Run bundle 之后，SQLite 里那条 Run 还在（账本不受保留策略管），
于是必然出现「库里有 Run、盘上没 trace」。这个事实记进**独立的 `trace_prunes` 表**
（`run_id` 主键、`prune_requested_at`、`absence_confirmed_at`、闭合 `prune_reason`），
**不改写 telemetry，也不动 `trace_incomplete`**。

`trace_incomplete` 是 Run 收尾时的**观测**——那一刻写盘成没成功；
裁剪是几十天后的**运维动作**。把后者写进前者那一列，两个再也分不开，
而它们的判读后果完全不同：一个指向"当时出了问题"，一个指向"到期了，正常"。

只靠一个"清到哪一天"的截止日期是不够的：它分不出**容量裁剪、删除失败、
人工移除、真正损坏**四种情况。有裁剪行即本系统主动删除、原因精确；
**无行却缺 trace** 才表示人工移除或损坏。

## 几处必须说清的边界

`absence_confirmed_at` 是"确认目录已消失"的时刻，**不得声称为实际 `unlink` 时刻**——
那个时刻我们证明不了，而一个声称精确却证明不了的时间戳，是审计件里最坏的一种字段。

**不外键依赖消息行**：屏障之前就崩掉的 Run 照样可能在盘上留下 bundle，
那条消息行可能从未落库。

`prune_reason` 闭合四值，并规定**确定性优先级 `manual` > `disk_low` > `age` > `capacity`**——
一次删除可能同时满足多条，优先级保证记录可复现。
**"删除失败"不属于这一族**：它不是删除的*原因*，而是恢复状态
（`retention-state.json` 的 pending 残留）所表达的*状态*。

## Consequences

裁剪要写库，因此必须跑在 `RuntimeHost` 的唯一写连接建立之后。
这不与单写者不变式冲突：取得进程锁之后即可先建立那条连接，再执行裁剪，
不需要第二条连接。

`retention-state.json` 只承担**崩溃恢复**，不是"上次报告"：
先原子替换写入 `{run_id, reason, requested_at}` 并 `fsync` 父目录，才允许真正删除；
删除后只收集**确认消失**的，用一个批事务写入生命周期事实；
失败项保留在 pending 并附错误，不得整批清空。启动时 pending 非空则先对账再裁剪——
`rmtree` 不原子留下的半删目录，正是靠这一步收尾。
