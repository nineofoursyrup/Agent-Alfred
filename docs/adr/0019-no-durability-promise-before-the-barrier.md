# trace 在持久性屏障之前没有持久性承诺

`TraceSink` 的 drain 线程逐条写入 `trace.jsonl`（无缓冲二进制 fd + 完整写循环），
但 **`fsync` 全程只在持久性屏障处发生一次**
（[ADR-0004](0004-flush-barrier-at-run-end.md)）。逐条 `fsync` 会把每个 Run 的本地写
放大到几百次同步，而它想买的东西已经有人买过了：崩溃丢掉末尾若干条的后果，
正是 [#3](https://github.com/nineofoursyrup/Agent-Alfred/issues/3) 那条
「末尾缺 `run.finished` 即未正常收尾」判读规则覆盖的场景。

代价必须写在明处：**`flushed` 这个词只在屏障处成立**。屏障之前，
`trace.jsonl` 对崩溃没有任何持久性承诺。

## 单一 drain 线程保证不交错，但不保证行原子

一个 Run bundle 只有一个写者，因此记录之间**不会交错**。
但 `write(2)` 可以在任意字节处被崩溃截断，所以行原子性**得不到保证**。

由此定死读取器契约：**只容忍唯一一条位于末尾的截断记录**，并据此判该 bundle
追踪不完整；**任何内部坏行一律失败**，不得跳过后继续读。
能跳过坏行的读取器会把一份损坏的审计件读成完好的——那比读不出来坏得多。

这条契约成立的前提，是写入端保证残留文件永远是**无内部空洞的连续前缀**：
写失败在有限重试后的首个不可恢复错误处**熔断到 Run 粒度**，保存首个原因与闭合
`reason_code`，后续事件只计丢弃数。"继续尽力写"会产出一个洞洞百出、
却长得像完整 trace 的文件，而它会被当成完整的来读。

## Consequences

屏障的 `fsync` 有确定次序：排空队列后，依次同步**工件文件 → `trace.jsonl` → `artifacts/` → Run 目录**。
`meta.json` 与日期目录已在发布时同步过（[ADR-0017](0017-run-bundle-is-the-atomic-unit.md)），不重复。

熔断是 **Run 粒度，不是进程粒度**：下一个 Run 重新尝试发布新 bundle。
写盘出问题从来不该让此后所有 Run 都失去追踪。
