# 模型指派与证据语义：连接观测不参与指派，用户声明不是系统验证

Models 页上有两个看起来都该管「这个模型能不能用」的维度：端点的**连接四态**
与模型的**支持三态**。把它们合起来判断「能不能选它」，是最自然的写法，我们**不这么做**。

**连接观测不参与模型指派。** 可指派的判据只有两项：
`pinned && (supported || (unknown && 手选 style 属于本版已实现的形状))`。
理由是连接观测**不持久化**——进程一重启，凡有密钥的端点一律回到 `已配置未测试`。
若让它 gate 指派，每次重启后全体模型集体不可指派，而用户什么也没做错。
那是把「我们还没测过」渲染成「你不能用」，与把「功能尚未实现」塞进连接四态是同一种混维。
端点连不上是**发消息那一刻**的运行事实，届时如实失败为 `endpoint_unconfigured`，
不是选模型那一刻的准入条件。

**用户手选 wire style 之后，支持三态仍是 `unknown`。** 手选写的是
`wire_style_override`，呈现为 `wire_style_source = user_declared`（「未验证，按你选择的形状尝试」），
而 `support_basis` 只记系统自己的依据（`builtin_table` / `probe_evidence`）。
把用户的**声称**翻转成系统的**结论**，会让一个选错形状的人先看到绿色的「支持」、
再收到一串 400。这条同时保住了自动翻转的空间：`unknown → unsupported`
仍可由白名单证据推动，因为那一格从来没被用户的声明占据过。

## Consequences

「能不能选」与「此刻通不通」在界面上是**两处独立的话**，不合成一句。
四态只出现在端点组头，三态只出现在模型行；任何被禁用的控件必须给出机器可读原因码，
并注明它属于哪一维。允许出现看似矛盾的组合（端点已连接 + 模型 unsupported），
两处各说各的——那不是 bug，那正是两维正交的可见形态。

用户因此可以把主模型指到一个**没有密钥**的端点上。这是刻意的：
配密钥与选模型是两件事，强行按顺序绑定只会让「先有鸡还是先有蛋」变成用户的问题。
